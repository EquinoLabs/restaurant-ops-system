## 1. Executive Summary & Verdict

### 1.1 Verdict on the "Add Operator" Slice
**Verdict: YES, "Add Operator" (`operator_creation`) remains the correct, lowest-risk first vertical slice**, but **it is currently only partially implemented and inconsistent with end-to-end governance**.

Specifically:
- **What is already built:** 
  - Centralized database schema (`approval_requests`, `approval_clarifications`) applied to Neon at revision `0015_approval_workflow_schema`.
  - Backend execution dispatcher for `operator_creation` ([`backend/app/modules/approvals/execution.py:190-209`](file:///C:/Lakshya/Coding/EquinoLabs/restaurant-ops-system/backend/app/modules/approvals/execution.py#L190-L209)).
  - Domain service [`create_platform_operator`](file:///C:/Lakshya/Coding/EquinoLabs/restaurant-ops-system/backend/app/modules/businesses/platform_service.py#L1174-L1290) implementing caller-owned transaction semantics (`db.flush()` only).
  - Read & Decision API (`GET /platform/approvals`, `GET /platform/approvals/{id}`, `POST /platform/approvals/{id}/decide`).
  - Read & Decision UI in Platform Admin (`PlatformApprovals.tsx`).
- **What is missing / broken:**
  1. **No Submission API Endpoint:** There is no HTTP endpoint (`POST /api/v1/platform/approvals`) for submitting approval requests.
  2. **UI Action Bypass:** The "Add Platform Operator" UI ([`AddOperatorModal.tsx`](file:///C:/Lakshya/Coding/EquinoLabs/restaurant-ops-system/apps/platform-admin/src/features/platform-admin/AddOperatorModal.tsx#L63)) bypasses the approval engine entirely and calls direct execution (`POST /api/v1/platform/operators`).
  3. **Credential Vulnerability in Execution Dispatcher:** Because `sanitization.py` denylists passwords in `payload_snapshot`, the execution handler falls back to a hardcoded string: `payload.get("password") or "AutoGeneratedSecretTemp123!"` ([`execution.py:200`](file:///C:/Lakshya/Coding/EquinoLabs/restaurant-ops-system/backend/app/modules/approvals/execution.py#L200)).
  4. **Unreachable Retry Logic:** Requests whose execution fails (`status='approved', execution_status='failed'`) cannot be re-executed via the decision endpoint because [`decide_approval_request`](file:///C:/Lakshya/Coding/EquinoLabs/restaurant-ops-system/backend/app/modules/approvals/service.py#L164) rejects non-pending requests with HTTP 422.

## 4. Findings on Execution-Design Concerns (Task 3)

### (a) Plaintext Temporary Passwords in Persisted Snapshots
- **Evidence:** [`approvals/sanitization.py:11-29`](file:///C:/Lakshya/Coding/EquinoLabs/restaurant-ops-system/backend/app/modules/approvals/sanitization.py#L11-L29) explicitly denylists `password` and `owner_password`. Line 100 raises `ValidationError` if present.
- **Consequence:** Staging a cleartext password in `payload_snapshot` is properly blocked. However, [`execution.py:200`](file:///C:/Lakshya/Coding/EquinoLabs/restaurant-ops-system/backend/app/modules/approvals/execution.py#L200) falls back to `"AutoGeneratedSecretTemp123!"` because the password was scrubbed.
- **Severity:** **High (Security Hazard)**.
- **Recommendation:** Do not store passwords in `payload_snapshot`. Instead, have the execution handler generate a cryptographically secure random temporary password (or activation token) upon approval, and securely provide it once to the approver or via a development credential file.

### (b) Status and Execution Status Decoupling on Failure
- **Evidence:** [`approvals/execution.py:402-488`](file:///C:/Lakshya/Coding/EquinoLabs/restaurant-ops-system/backend/app/modules/approvals/execution.py#L402-L488) executes a domain rollback, retains `status = 'approved'`, updates `execution_status = 'failed'` (or `'blocked'`), captures sanitized `execution_error`, and commits the failure record in an isolated transaction.
- **Severity:** **None (Verified Sound)**.
- **Recommendation:** Retain current pattern.

### (c) Idempotent Retry Reachability vs HTTP 422
- **Evidence:** [`approvals/service.py:164`](file:///C:/Lakshya/Coding/EquinoLabs/restaurant-ops-system/backend/app/modules/approvals/service.py#L164) checks:
  ```python
  if req.status not in (ApprovalStatus.PENDING, ApprovalStatus.NEEDS_INFORMATION):
      raise ValidationError("Cannot decide approval request with status ...")
  ```
- **Consequence:** If a request is `approved` but execution failed (`execution_status = 'failed'`), calling `/decide` fails with HTTP 422. The retry logic in `execution.py` (`retry_count += 1`) cannot be triggered via the HTTP API.
- **Severity:** **High (Operational Blocker for Recovery)**.
- **Recommendation:** Add a dedicated endpoint `POST /api/v1/platform/approvals/{id}/retry` or allow `decide` to re-execute when `status == 'approved'` and `execution_status == 'failed'`.

### (d) Reject Path Commit vs Audit Logging
- **Evidence:** [`approvals/service.py:173-197`](file:///C:/Lakshya/Coding/EquinoLabs/restaurant-ops-system/backend/app/modules/approvals/service.py#L173-L197) flushes the `status = 'rejected'` update, calls `log_audit(...)`, and then executes a single `db.commit()`.
- **Consequence:** If audit logging fails, the transaction rolls back. An unaudited rejection is impossible.
- **Severity:** **None (Verified Sound)**.

### (e) Password Exposure through Secondary Channels
- **Evidence:** Audit metadata in `platform_service.py:1281` records only `target_user_id`, `target_email`, and `new_role`. No password or hash is logged. `ApprovalRequestDetailOut` excludes passwords.
- **Severity:** **Low**.
- **Recommendation:** Maintain strict omission of credential keys from `metadata_json`.

### (f) Partial Unique Index on Pending Requests
- **Evidence:** Migration 0015 has a partial unique index on `idempotency_key`, but not on `(request_type, target_entity_id)` for pending requests.
- **Consequence:** For Mode 2 (new operator by email), `target_entity_id` is null. Multiple pending requests for the same email can be submitted if different idempotency keys are used. The second request fails only upon approval execution.
- **Severity:** **Medium**.
- **Recommendation:** Enforce client-side idempotency keys and check for duplicate pending emails in `check_can_create_request` before persistence.

### (g) SQLite vs PostgreSQL Differences
- **Evidence:** `with_for_update()` and `pg_advisory_xact_lock` are conditional on PostgreSQL dialect in `execution.py:56` and `platform_service.py:108`. Tests in `test_approval_service_and_execution.py` pass cleanly on SQLite, while `test_postgres_concurrency.py` tests row locks on PostgreSQL.
- **Severity:** **Low (Handled Gracefully)**.

### (h) Commit-Outcome Uncertainty Recovery
- **Evidence:** [`execution.py:405-435`](file:///C:/Lakshya/Coding/EquinoLabs/restaurant-ops-system/backend/app/modules/approvals/execution.py#L405-L435) tracks `commit_dispatched`, queries `populate_existing()` on lost connections, preserves `SUCCEEDED` if committed, and raises `CommitOutcomeUncertainError` when ambiguous. Frontend `PlatformApprovals.tsx:160` handles this error code with guidance.
- **Severity:** **None (Verified Sound)**.

### (i) Authorization and Tenant Boundaries
- **Evidence:** `operator_creation` is platform-wide (`business_id=None`). Lines 98-106 in `execution.py` enforce that `business_id` is strictly null for platform-wide types, preventing tenant bleed.
- **Severity:** **None (Verified Sound)**.

## 7. Recommended Next Step & Test Plan (Task 6)

### 7.1 Scope of Slice 1: End-to-End Operator Approval Submission & Execution
Do not rebuild models, migrations, or the decision endpoint. Focus strictly on closing the submission and credential gap:

```mermaid
flowchart LR
    A["AddOperatorModal.tsx"] -->|1. Submit Request| B["POST /api/v1/platform/approvals"]
    B -->|2. Create 'pending'| C[("approval_requests Table")]
    D["Approver (PlatformApprovals.tsx)"] -->|3. POST /approvals/{id}/decide| E["execute_approval_request"]
    E -->|4. Generate Safe Password| F["create_platform_operator (commit=False)"]
    F -->|5. Hash & Insert| G[("users Table")]
    E -->|6. Append Credential| H["backend/.local-user-credentials.txt"]
```

### 7.2 Implementation Steps

#### Step 1: Add Approval Request Submission Endpoint
- **File:** `backend/app/api/v1/approvals.py`
- **Objective:** Add `POST /api/v1/platform/approvals` accepting `request_type`, `target_entity_type`, `payload`, and `justification`.
- **Validation:** Calls `create_approval_request` with caller as requester.

#### Step 2: Fix Credential Generation in Operator Execution Handler
- **File:** `backend/app/modules/approvals/execution.py`
- **Objective:** Remove static `"AutoGeneratedSecretTemp123!"`. Generate random temporary password via `secrets.token_urlsafe(16)` when provisioning Mode 2.
- **Local Dev Artifact:** Append entry to `backend/.local-user-credentials.txt` post-commit (if local dev environment). Ensure `.gitignore` ignores this file.

#### Step 3: Wire Frontend Add Operator Modal to Approval Submission
- **File:** `apps/platform-admin/src/features/platform-admin/AddOperatorModal.tsx`
- **Objective:** When submitted by an Admin or Operator, submit an approval request via `createApprovalRequest(...)` instead of directly calling `createPlatformOperator`. Show success feedback: *"Operator approval request submitted for review."*

### 7.3 Test Plan
1. **Authorization Tests:** Operator and Admin can submit `operator_creation` requests; unauthorized tenant users get 403.
2. **Password Protection Tests:** Submitting plaintext password in `payload` fails sanitization validation with 422/400.
3. **Execution Credential Verification:** Approved operator account has valid bcrypt hash; static password `"AutoGeneratedSecretTemp123!"` is eliminated.
